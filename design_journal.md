# Ubuntu Sponsoring Bot: Design Journal

This document tracks major architectural and design decisions made during the development of the bot, along with the rationale behind them. For term definitions (both general Ubuntu/Launchpad sponsoring vocabulary and this bot's own concepts like "facts" or "inconclusive"), see [`GLOSSARY.md`](GLOSSARY.md).

## 1. Hybrid Architecture (Deterministic Scripts + LLM Evaluator)
**Date:** 2026-06-29
* **Decision:** Split the triage process into two phases: a deterministic Python script phase, and an LLM dispatcher phase.
* **Rationale:** We want to limit expensive, slow, and non-deterministic LLM calls to tasks that actually require qualitative human-like judgment (e.g., evaluating the quality of an SRU template). Deterministic tasks (e.g., checking if an MP is targeting the correct branch) are handled instantly and 100% reliably by basic Python logic.

## 2. State Management via Local SQLite
**Date:** 2026-06-29
* **Decision:** Use a lightweight `sqlite3` database (`state.db`) to track the status of each Bug/MP URL (e.g., `NEW`, `DONE`, `PENDING_LLM_REVIEW`).
* **Rationale:** This decouples the bot from needing a complex background worker queue (like Celery/Redis). It allows the bot to be invoked repeatedly via a simple cron timer. By persisting state locally, we avoid re-fetching and re-triaging the same URLs from Launchpad, saving significant time and API quotas.

## 3. Launchpad API: `python-launchpadlib` vs `lpcli`
**Date:** 2026-06-29
* **Decision:** Use `python-launchpadlib` for the Python deterministic scripts, rather than wrapping the `lpcli` tool via subprocess.
* **Rationale:** `lpcli` is a great tool for LLM agents because it outputs human-readable text. However, for a programmatic Python orchestrator, `launchpadlib` provides native, structured Python objects. This eliminates the need for brittle regex parsing of CLI outputs and handles authentication securely via the system keyring.

## 4. LLM Orchestration: `opencode` CLI vs Python API Libraries
**Date:** 2026-06-29
* **Decision:** The Python LLM Dispatcher invokes the LLM by calling the `opencode` CLI via `subprocess.run`, rather than using the `openai` Python package.
* **Rationale:** 
  1. **Agents as a Service:** It allows us to seamlessly leverage existing shared agent skills in the future (e.g., `opencode run --skill sru-review`) without having to rewrite prompt orchestration logic in Python.
  2. **Zero Config:** The Python code remains completely agnostic to API keys, model endpoints, and providers. It inherits whatever the environment has configured for `opencode`.
  3. **Consistency:** This architecture is proven and mirrors the team's existing `pmtriage` workflow.

## 5. Fetching the Queue via JSON endpoint
**Date:** 2026-06-29
* **Decision:** To process the entire queue automatically (`--all`), the bot fetches `https://sponsoring-reports.ubuntu.com/jsons/sponsoring.json` rather than querying the Launchpad API directly.
* **Rationale:** Launchpad API queries for complex project states often timeout. Reading the pre-generated JSON guarantees we parse exactly what the human patch pilots see on the frontdesk dashboard, instantly and without load on the Launchpad API.

## 6. Interactive API Write Confirmations
**Date:** 2026-06-29
* **Decision:** All Launchpad API write operations (comments, status changes, unsubscribing) explicitly prompt the user for a `[y/N]` confirmation in the console.
* **Rationale:** While in the active iteration and development phase, it prevents the bot from making unilateral, destructive actions on real bugs and MPs. It keeps the developer "in the loop" while still automating the read/triage logic.

## 7. Dropping Legacy Bazaar Support for MPs
**Date:** 2026-06-29
* **Decision:** The deterministic checks for Merge Proposals only parse Git properties (e.g. `target_git_path`). Legacy Bazaar checks were removed.
* **Rationale:** Launchpad is phasing out support for bzr. Maintaining dual Git/Bazaar support logic adds unnecessary technical debt for a system that will soon be deprecated.

## 8. Handling Merge Proposal Queue Semantics
**Date:** 2026-06-29
* **Decision:** The bot does *not* attempt to `unsubscribe()` the sponsor team from Merge Proposals. Instead, it relies on Launchpad's native queue mechanics (changing an MP to `Needs fixing`, `Merged`, or `Rejected` naturally drops it from the sponsor queue).
* **Rationale:** Unlike Bug Tasks, the Launchpadlib API does not provide a direct method to arbitrarily unsubscribe teams from an MP review request. Attempting to force an unsubscribe caused errors, and it is architecturally cleaner to let Launchpad's status transitions handle queue visibility automatically.

## 9. Structured LLM Verdicts with Fail-Safe Parsing
**Date:** 2026-06-29
* **Decision:** The LLM reviewer asks opencode to end its reply with a fenced `yaml` block (`verdict: pass|fail`, `reason:`) and parses that, instead of string-matching prose for `PASS`. Parsing fails safe: any missing/malformed block, a non-`fail` verdict, or a `fail` without a reason routes the item to a human (`READY_FOR_HUMAN`) — only an explicit, well-formed `fail` with a reason triggers an automated rejection.
* **Rationale:** Agent output is chatty and non-deterministic; `startswith("PASS")` mis-fires and, worse, failed *toward* rejecting contributors. Mirrors pmtriage's YAML-block extraction. The bug description is also fenced as untrusted data. The agent only ever produces a *recommendation*; it never holds Launchpad write credentials (the orchestrator executes writes), so injection cannot act on the real tracker.

## 10. Facts-Based Re-Triage (replaces conclusive DONE)
**Date:** 2026-06-29
* **Decision:** Per URL we store a `facts` snapshot of the *contributor-controlled* signals our checks key on (MP target branch, diff identity, conflicts; bug description, tags, task statuses) and (re-)triage only when those change. The old "`DONE` → skip forever" logic is gone; `status` is now informational.
* **Rationale:** "Needs fixing" MPs stay in the sponsoring queue, so the bot re-sees them every run. Conclusive `DONE` meant a contributor who fixed their MP was never re-reviewed. The snapshot deliberately **excludes bot-mutated fields** (e.g. an MP's `queue_status`) — otherwise the bot would detect its own action and nag forever. This is the sponsoring-bot equivalent of pmtriage's `facts.yaml` change-detection.

## 11. Explicit Write Modes (resolves cron vs interactive contradiction)
**Date:** 2026-06-29
* **Decision:** Three explicit write modes: `--dry-run` (default; log intended writes, do nothing), `--interactive` (`[y/N]` prompt), `--yes` (unattended). Interactive with no TTY refuses to write rather than calling `input()`.
* **Rationale:** Decisions #2 (cron) and #6 (interactive `[y/N]`) contradicted: under cron there is no TTY and `input()` raises `EOFError`. Modes make the intent explicit and safe-by-default, and close the crash path.

## 12. Launchpad as the Source of Truth for Comment Dedup
**Date:** 2026-06-29
* **Decision:** Before posting, compare the comment's author to the bot's own account (`self.lp.me`, the `~ubuntu-sponsoring-bot` identity) and skip only when an **identical** comment by the bot already exists. No marker text; no reliance on local state.
* **Rationale:** Local SQLite is not durable across machines or `state.db` loss. Checking Launchpad itself prevents re-spamming. Matching on identity + exact content (not "ever commented") preserves legitimate back-and-forth where a changed request leads to a new, different comment.

## 13. Admin Check Scoped to the Relevant Ubuntu Series
**Date:** 2026-06-29
* **Decision:** The "already fixed" check ignores upstream/Debian tasks and looks only at the Ubuntu tasks for the request's `source_package` (threaded from the queue JSON). It unsubscribes only when every relevant Ubuntu-series task is closed (`Fix Released`/`Fix Committed`, or `Won't Fix`/`Invalid` for untargeted series) **and** at least one actually landed.
* **Rationale:** The old code unsubscribed if *any* single task was `Fix Released` — an upstream fix or one landed series would wrongly drop the whole bug off the queue while other series still needed sponsoring.

## 14. Tests and an Audit Trail
**Date:** 2026-06-29
* **Decision:** A `pytest` suite (matching pmtriage's layout) covers verdict parsing, the facts lifecycle, write-mode/TTY gating, comment dedup, and the admin-check matrix. Every write attempt — including dry-run and skips — is appended to an `audit.jsonl` log (timestamp, url, action, target, mode, outcome).
* **Rationale:** The bot mutates a public community tracker; `print` is not a record and one-shot manual checks are not regression protection. `LPClient` accepts injected `lp`/`audit` so the suite runs without authenticating to Launchpad.

## 15. Launchpad Auth via a Persisted Credentials File
**Date:** 2026-06-29
* **Decision:** `LPClient` authenticates with `Launchpad.login_with(..., credentials_file=..., launchpadlib_dir=...)`, persisting the OAuth token to `~/.cache/ubuntu-sponsoring-bot/credentials` (env-overridable via `SPONSORING_BOT_LP_CREDENTIALS` / `SPONSORING_BOT_LP_CACHE`). Matches pmtriage and ubuntu-sponsoring.
* **Rationale:** The default `login_with` persists via the system keyring; in a headless container the keyring backend is `fail`, so the token is never stored and every run re-prompts for browser authorization — fatal for unattended/cron operation. A credentials file means authorize-once, then non-interactive. (Token is stored unencrypted at mode 0600, the accepted trade-off for a bot account, as in the sibling services.)

## 16. MP Conflict Detection via `preview_diff.conflicts`
**Date:** 2026-06-29
* **Decision:** Merge-conflict state is read from `preview_diff.conflicts` (a string listing conflicting files; empty means none), in both `checks.check_mp_conflicts` and `facts.build_facts`.
* **Rationale:** A read-only smoke test against a real MP showed there is no `has_conflicts` attribute on a `branch_merge_proposal`. The previous `getattr(lp_obj, 'has_conflicts', False)` therefore always returned `False`, silently disabling the conflict check. Unit tests shared the same wrong assumption, so only hitting production surfaced it — which is why the smoke-test gate exists.

## 17. Bouncing a Bug Sets It Incomplete (and Keeps Sponsors Subscribed)
**Date:** 2026-06-29
* **Decision:** When the LLM bounces a bug as `INCOMPLETE` (SRU/sync), `main` now sets **every open Ubuntu task** to `Incomplete` (`LPClient.set_bug_tasks_incomplete`) in addition to commenting. It no longer unsubscribes `~ubuntu-sponsors` — sponsors stay subscribed for visibility. Already-resolved tasks (Fix Released/Committed, Won't Fix, Invalid) and already-Incomplete tasks are skipped.
* **Rationale:** `Incomplete` is the canonical Launchpad status for "waiting on the submitter" (and Launchpad auto-expires stale Incomplete bugs). Previously the bug status was untouched and only the bot's internal state recorded the bounce.
* **Fix #2 tie-in:** task statuses are part of the bug fingerprint, and the bot now mutates them. So `set_bug_tasks_incomplete` returns the tasks it changed and `main` folds them into the persisted facts via `facts.apply_task_status_changes` — the bot's own status write is not mistaken for a contributor change on the next run. Only a later *contributor* status change re-triggers triage.

## 18. Sync Request Triage Sub-Flow (DONE)
**Date:** 2026-07-01
* **Decision:** A sync request is always a bug matching `_is_sync` (never an MP — a sync is a source-package copy, there is no code to review). Implemented in `llm_reviewer._triage_sync`/`_parse_sync_title` (called from `triage_bug`) plus the archive-lookup module (`archive_lookup.py`, see #21), `LPClient.set_bug_tasks_fix_released`, and a new `SYNCED` conclusive status in `main.py`. Tests: `tests/test_archive_lookup.py`, `tests/test_sync_triage.py`, `tests/test_synced_status.py`. Sub-flow, captured in `sync_triage.dot`:
  1. **Delta detection:** the currently published Ubuntu version's revision containing `ubuntuN` means there is a delta; `buildN` (no-change rebuild) does not count.
  2. **No delta →** (1.a) Ubuntu archive state against `$devel`/`$devel-proposed`: if the requested-or-newer version is already there, set the matching Ubuntu task(s) to `Fix Released` and comment — "matching" means the task with no series target, or the one nominated to `$devel` if a human targeted it (syncs only ever land in `$devel`). (1.b) Otherwise the Debian archive: the requested version must be in `unstable`, or `experimental` if the title/description says so. If it's not found in the stated pocket, an LLM check reads the description for a specific justification (e.g. an unusual case) before deciding: justified → leave for human, no write; unjustified → comment + `Incomplete`.
  3. **Has delta →** (2.a) reuse the existing `review_sync_request` LLM check (delta explained and justified as droppable) — this already existed but was previously fired unconditionally for every sync-titled bug instead of gated on delta actually being present. (2.b, backlog) verify "this is already in Debian" delta claims are actually true, rather than trusting the submitter's word.
* **Rationale:** Mirrors the fail-safe stance used elsewhere (LLM only asked to judge things Python can't determine deterministically; ambiguity routes to a human, never an auto-reject). The archive-lookup primitives are the same ones the target-branch check will use ([[mp-target-branch-rules]]), so both checks should eventually share one small helper.
* **Version comparison:** uses `apt_pkg.version_compare` (python3-apt), not shelling out to `dpkg --compare-versions` — same C library, no extra process, and it's what `main.py`'s CI now installs `python3-apt` for. `apt_pkg` is a compiled extension tied to the *system* Python, so it isn't pip-installable; CI (`.github/workflows/ci.yml`) had to stop using `actions/setup-python`'s isolated interpreter and install dependencies against the runner's system python3 instead.

## 19. Feature Freeze Exception for Sync Requests (BACKLOG)
**Date:** 2026-07-01
* **Decision:** After a cycle's Feature Freeze, a sync request that brings in a new feature (not just a bug fix) needs a FeatureFreezeException (FFe) before it can be sponsored — see https://ubuntu.com/project/docs/release-team/freezes/ for what Feature Freeze means (that page has no dates; it's a process-definition page only). For now, `release_schedule.py` holds `FEATURE_FREEZE` as a hand-maintained `datetime.date` constant (currently `2026-08-20`, confirmed by seb128; `None` fails safe to "no freeze in effect" if ever left unset) plus `is_after_feature_freeze()`. **Not yet wired into `_triage_sync`** — two pieces are still needed and explicitly deferred:
  1. Sourcing `FEATURE_FREEZE` from an online release schedule automatically instead of hand-editing it every cycle.
  2. Determining whether a given sync actually introduces a new feature (vs. a bug fix) — deferred to future shared-skill work (seb128: "we are working on shared skills for that that we will leverage"), not a bespoke LLM prompt here.
* **Rationale:** Recording the constant and the branch now (in the diagram and this journal) so the shape of the check is visible before its two prerequisites land, without guessing at either the freeze-detection heuristic or a specific freeze date I'm not certain of.

## 20. `check_target_branch` Is Wrong (DONE)
**Date:** 2026-07-01, implemented 2026-07-02/03
* **Problem:** `checks.check_target_branch` (`checks.py`) bounced **any** MP targeting `ubuntu/devel` with "should target `debian/sid` (LP #1976112)". This false-rejects legitimate contributions: the correct target is a function of the **contribution type**, not a blanket `debian/sid`. Caught live: MP #507686 (a plain fix, branch `fix-lp2155031`) was bounced with this message, which is wrong — it's not a merge.
* **Correct mapping (confirmed by seb128, 2026-07-01):**
  - Merge based on Debian **unstable** → target `debian/sid`
  - Merge based on Debian **experimental** → target `debian/experimental`
  - **SRU** upload → target `ubuntu/<series>` (e.g. `ubuntu/jammy`), NOT `ubuntu/devel`
  - **Ubuntu-only** change on devel → `ubuntu/devel` is legitimate (the old check false-rejected this)
* **The real gap wasn't sid-vs-experimental, it was merge-vs-not:** the original design (below) assumed we'd already know an MP was a merge and only needed to pick sid vs. experimental. What actually broke was more basic — the code had **no notion of "is this MP a merge at all"**, so it applied the merge-only debian/* rule to every MP. seb128 proposed four candidate signals for that classification: (a) changelog text "Merge with Debian"/"Remaining changes", (b) source branch name contains "merge-", (c) target branch is already `debian/*` (circular — that's the field in question), (d) a linked bug titled "merge $sourcepackage".
* **Validated live** (seb128 + assistant, 2026-07-02) against the real `~ubuntu-sponsors` queue (52 open MPs) and specific examples (`#507686` fix, `#506637`/plocate, `#506104`/sudo, `#506826`/gnutls28 merges): **(b) is a clean, empirically 100%-accurate signal on its own** — every merge MP's `source_git_path` contains "merge" (`merge/4.7.1-2`, `merge-lp2153358-stonking`, `merge-1.24-1.23-stonking`, ...); every fix MP's doesn't. It's also free — `source_git_path` is already on the MP object, no extra API call. (d) was independently confirmed too (e.g. bug #2153346 linked to the plocate MP is titled "Merge plocate from Debian for stonking cycle") but in every sample checked it was redundant with (b) — same bug number embedded in the branch name either way.
* **Implemented (`checks._is_merge_proposal`, `checks.py`):**
  1. Primary: `"merge" in source_git_path.lower()` (case-insensitive substring, free).
  2. Fallback (only when (1) doesn't match, costs one extra API call): `lp_obj.bugs` — merge MP if any linked bug's title matches `^(please\s+)?merge\b`. Catches merge MPs that don't follow the branch-naming convention.
  3. Neither signal → not a merge → `ubuntu/devel`/`ubuntu/<series>` is legitimate, `check_target_branch` returns `False` (no bounce). This is the fix for #507686-style false positives.
  4. Merge MP confirmed, target isn't `debian/*` → bounce (unchanged comment/status-change path).
* **(a) not implemented:** the changelog-text signal wasn't needed once (b) proved 100% accurate on live data; kept as a documented fallback option if (b)/(d) ever prove insufficient, not built speculatively.
* **Sid vs. experimental (implemented 2026-07-03, `checks._debian_target_suite`):** once a merge MP is confirmed mistargeted, the bounce comment now names the specific branch rather than a generic "either one":
  1. **Diff-context (primary, no extra I/O beyond the diff fetch itself):** confirmed live against `preview_diff.diff_text` for both #507686 and the real sudo merge #506104 (with the bot's authenticated session — the earlier 401 was specific to an *anonymous* session; `preview_diff.diff_text` needs `launchpad.View`, which any logged-in session, including the bot's, has). A merge prepends the new Ubuntu changelog entry to the top of `debian/changelog`; the first *context* line just below the added block is the header of the Debian entry the merge is based on — same version modulo the trailing `ubuntuN`, and its suite (unstable/experimental) is exactly the suite to target. `checks._changelog_diff_lines` isolates the `debian/changelog` hunk from the raw diff text; `_debian_target_suite` walks it for the first post-added-block context line matching a changelog-header regex.
  2. **archive_lookup fallback (only if (1) is inconclusive):** derives the Debian version from the proposed Ubuntu version — read from the diff's own added changelog header, not re-fetched — strips the trailing `ubuntuN`, and checks which of `unstable`/`experimental` holds *exactly* that version via `archive_lookup.debian_versions(pkg)` (package name parsed from the MP's own URL, `.../+source/<pkg>/+git/...`). Ambiguous (both/neither match) → `None`, same as diff-context failing.
  3. Neither resolves → falls back to the original generic phrasing ("`debian/sid` (or `debian/experimental`, matching the Debian suite you uploaded to)"). Never guesses.
  4. No live example to validate the full bounce-with-precise-suite path against: every merge MP in the live queue is already correctly targeted (see the #507686/#506104 checks above), so this specific combination (merge + mistargeted + suite resolvable) only exists in synthetic tests, built from the real diff shapes captured from #506104/#507686.
* **Fail-safe stance (unchanged, and extended to the new merge-detection and suite-detection heuristics):** only bounce when the MP is positively identified as a merge **and** the target clearly mismatches; only name a specific suite when it's positively resolvable, otherwise fall back to the generic phrasing rather than guess. A false-negative (missed bounce, or generic instead of specific phrasing) is safe; a false-positive isn't.
* **Explicitly out of scope for this check:** SRU is a bigger case than just target-branch — an SRU also needs a bug with a valid SRU template and to be fixed in newer series too (no regression on release upgrade), etc. Deferred, see #19-style backlog entry when that gets designed.
* **Tests:** `tests/test_mp_checks.py` — merge MP mistargeted (bounced), fix MP on `ubuntu/devel` (not bounced, the regression case), SRU-shaped MP on `ubuntu/<series>` (not bounced), merge detected via linked-bug-title fallback, unrelated bug title doesn't trigger a bounce, `_is_merge_proposal` fails safe (returns not-a-merge) when `lp_obj.bugs` raises, `_debian_target_suite` from diff-context (both suites), from the archive_lookup fallback, ambiguous-archive-lookup → `None`, nothing-resolvable → `None`, and the bounce comment reflecting a resolved vs. generic suite phrase. `tests/fakes.py` gained `FakeHostedFile` (stands in for `HostedFile.open().read()`) and `FakeDiff(diff_text=...)`.

## 24. `--verbose` Decision-Step Logging (DONE)
**Date:** 2026-07-02
* **Problem:** the bot's output only ever showed the action taken when a check *fired* (e.g. "incorrectly targets ubuntu/devel..."); when a check silently returned `False`, nothing was printed. Debugging why check_target_branch fired wrongly for #507686 required re-deriving the logic path by hand instead of reading it off a run.
* **Decision:** standard-library `logging`, not a bespoke flag threaded through every function. Each module (`checks.py`, `llm_reviewer.py`, `main.py`) gets a module-level `logger = logging.getLogger(__name__)`; every decision branch (both "fired" and "skipped") gets a `logger.debug(...)` call describing what was evaluated and the result. `main.py`'s new `--verbose` flag just calls `logging.basicConfig(level=logging.DEBUG if verbose else logging.WARNING, ...)` once at startup — no parameter-passing through the call chain, and existing `print()` calls (the "an action was taken" messages) are untouched and still always shown.
* **Coverage:** `main.triage_url` logs each of the four deterministic checks' fired/skipped result; `checks.py` logs the *why* inside `check_administrative_state` and the new `_is_merge_proposal`/`check_target_branch`; `llm_reviewer.py` logs every branch of `_triage_sync`'s decision tree (delta detected?, already synced?, found in Debian?) and `triage_bug`'s SRU/sync routing decision.
* **Not covered yet:** `llm_reviewer.triage_mp` (still a stub, #4 in `STATUS.md`) and the SRU/sync LLM prompt-and-verdict calls themselves only log via existing `print()`/`WARNING` lines, not new `logger.debug` — revisit if `--verbose` output for those paths turns out to be needed too.

## 21. Archive Lookups Moved off `rmadison`/`distro-info` (DONE)
**Date:** 2026-07-01
* **Decision:** `rmadison.py` (the sync-triage archive-lookup module from #18) is replaced by `archive_lookup.py`, which drops the `rmadison`/`distro-info` CLI dependency entirely:
  - **Ubuntu versions & devel series** (`ubuntu_versions`, `devel_codename`) now come straight from the Launchpad API (`distributions["ubuntu"].current_series`, `archive.getPublishedSources(...)`) via the `lp` object `LLMReviewer` is now constructed with (`main.py` passes `lp_client.lp`) — reuses the bot's already-authenticated launchpadlib session rather than a second (anonymous) login.
  - **Debian versions** (`debian_versions`) now come from `https://qa.debian.org/madison.php?text=on&package=<pkg>[&s=<suites>]` over plain `urllib.request`, instead of shelling out to `rmadison -u debian`. Same madison-format text output (`pkg | version | suite | archs`), so the existing parser (`_parse_madison`, ex-`_parse`) is unchanged.
  - `has_ubuntu_delta`/`is_at_least` (`apt_pkg`-backed) are unchanged.
  - Fixed a latent bug while touching this: madison output keys a requested suite *alias* under its actual codename (e.g. asking for `unstable` gets a result keyed `sid`), so `_triage_sync`'s Debian lookup now takes `next(iter(debian_versions.values()), None)` instead of `debian_versions.get(target_suite)` — it already filtered to exactly one suite, so this doesn't need the key to match what was asked for.
* **Rationale (seb128):** questioned whether `rmadison` was the right source, suggesting Launchpad for Ubuntu and `qa.debian.org/madison.php` for Debian. Confirmed via live queries that madison.php is the *same* madison data `rmadison` itself queries (same freshness, just reachable over HTTP) — not fresher or staler; that staleness turned out to matter (see #22, #23).
* **Net effect:** no local `devscripts`/`distro-info` packages needed anywhere (dev machine or CI); CI's `python3-apt` install is still required (unrelated — `apt_pkg` is the version comparator, not an archive-query tool). Validated against real data (`archive_lookup` functions + `LLMReviewer()._triage_sync`, read-only, no writes) — see the bug used for #18's original validation.

## 22. Debian Publish-Lag Grace Window for Sync Requests (REVERTED — see #23)
**Date:** 2026-07-02
* **Problem:** madison (via #21, or the old `rmadison`, doesn't matter — same underlying archive data) reflects the Debian archive only *after* the publisher runs, which can lag a fresh upload by up to ~6h. Filing a sync request right after uploading to Debian is the normal workflow, not a bogus one — but `_triage_sync`'s 1.b branch would see "not found in Debian" and ask the LLM for a justification the submitter has no way to give (they didn't do anything wrong, the archive just hasn't caught up), leading to an unwarranted bounce.
* **Options considered:** (1) find a faster-updating upload-log source, e.g. `tracker.debian.org/pkg/<pkg>/news/` (shows accepted uploads before the publisher runs); (2) a deterministic age-based grace window using the bug's own creation time. Chose (2) at the time: no new dependency (`bug.date_created` is a field we already get), and it fit the bot's existing fail-safe pattern directly.
* **What was built (now reverted):** `llm_reviewer._DEBIAN_PUBLISH_GRACE = timedelta(hours=6)`; `_triage_sync(title, description, date_created=None)` skipped the LLM-justification check and routed straight to `READY_FOR_HUMAN` when the bug was younger than the grace window and the version wasn't found in Debian.
* **Why reverted:** seb128 checked with Gemini and got a better answer to the *actual* problem (madison's data source, not the bot's tolerance for staleness) — see #23. A live-data source makes the grace window's premise (archive is unavoidably ~6h stale) false, so the workaround is unnecessary complexity once the root cause is fixed instead.

## 25. MP Review Votes Replace Direct Status Writes (DONE)

## 26. Changelog LP Bug Reference Sanity Check (DONE)
**Date:** 2026-07-03
* **Problem (seb128):** a git-ubuntu changelog entry commonly cites an LP bug, e.g. `(LP: #1234567)`. Nothing checks that bug number is actually real for this package — a copy-paste/typo'd number would ship into the released changelog permanently. Ask: "if the changelog lists a launchpad bug, can we check that the reference is correct? easy check is to verify that the bug is against that package (the bug page can list several packages, it is enough to ensure the package is listed)."
* **Decision:** `checks.check_changelog_bug_reference` (Check 5, after `check_empty_diff`, before the LLM phase). Applies to any MP (not merge-specific, unlike Check 2) with a readable `debian/changelog` diff:
  1. `_source_package_from_mp` (reused from #20) gets the package name.
  2. `_lp_bug_numbers_from_new_changelog_entry` extracts LP bug numbers cited in the *new* entry only (`LP:? *#\d+`, colon optional — real examples use both `(LP: #123)` and `- foo (LP #123)`/`LP#123` forms in "Remaining changes" bullets).
  3. For each cited bug, `lp_client.lp.bugs[number]` is fetched and checked for any task whose `bug_target_name` is exactly the package or starts with `"{package} ("` — matches an Ubuntu, Debian, *or* any other task naming the package, per seb128 ("the bug page can list several packages, it is enough to ensure the package is listed").
  4. Any bug number with no matching task → comment (only the mismatched numbers are listed, not all cited ones) + `vote="Needs Fixing"` (see #25 for why a vote, not a status write). Severity confirmed by seb128 (2026-07-03): treat like the other deterministic bounces, not an FYI-only comment.
* **Fail-safe surface:** no bug reference cited, unreadable diff, undeterminable package, or a per-bug lookup failure (bug not found / no access) → skip that part rather than guess a mismatch. Only warns on a positive, checked mismatch.
* **A real bug found while validating, not built deliberately:** the naive first version scanned *every* `+`-prefixed line in the whole `debian/changelog` diff for bug references. Live-tested against real merge MP #506104 (sudo): the diff for that merge had **1472 of 1697** `debian/changelog` diff lines prefixed `+` — git-ubuntu's merge diff can show most of the file as "added" (git can't produce a small diff against sufficiently diverged history), not a clean top-of-file insert. The naive version picked up `LP: #1915250` from an entry several merges back that has nothing to do with this contribution — a false positive. Fixed by bounding the scan to the *first* changelog stanza only (stop at the second entry-header line seen among the added lines) — this works correctly whether the diff cleanly isolates just the new entry (the common case) or dumps most of the file as "+" (git-ubuntu merges). Regression test: `test_lp_bug_numbers_ignore_older_entries_swept_up_by_a_wholesale_diff`, built from this exact real-world shape.
* **Validated live** against both #507686 (xmltooling fix) and #506104 (sudo merge) post-fix: sudo's four cited bugs (`#2153358`, `#2026888`, `#2111419`, `#2115781`) are all genuinely against `sudo` → no warning (correct: this is the maintainer's own accurate delta documentation). xmltooling's `(LP: #2155031)` → **flagged**, and independently confirmed as a real mismatch: bug #2155031 is titled "xmlsec1: FTBFS with openssl 4.0" with tasks only against `xmlsec1` (a related but different package), not `xmltooling` — very plausibly copy-pasted from a sibling package's FTBFS bug while adapting the same OpenSSL-4.0 fix. Exactly the class of error this check is meant to catch.
* **Tests:** `tests/test_mp_checks.py` — match (no warning, both Ubuntu- and Debian-task cases), mismatch (warns, vote, correct package/bug number in the message), no-bug-cited (skip), lookup-failure (fail-safe skip, not a false mismatch), partial mismatch (only the actually-mismatched number listed), undeterminable package (skip), and the wholesale-diff regression test above.

## 27. Proposed Version vs. Archive Sanity Check (DONE, MPs only)
**Date:** 2026-07-03
* **Problem (seb128):** nothing checked whether the version an MP proposes is actually still ahead of the archive. Two failure modes slip through unnoticed: (a) someone else's upload landed with a higher version while this MP sat in the queue (stale), or (b) an upload with the exact same version already exists — either this MP's own change (already uploaded, just needs closing) or a genuinely different upload that reused the version number (needs a rebase). seb128 also flagged this is wanted for bug-attached patches too, not just MPs, but asked to start with MPs and put the bug/patch case in the backlog (reading a proposed version out of an attachment is a different extraction problem than reading it out of an MP diff).
* **Decision:** `checks.check_stale_version` (Check 6, after `check_changelog_bug_reference`, before the LLM phase). For any MP with a readable `debian/changelog` diff:
  1. `_proposed_changelog_entry` (new helper, shares the same first-stanza-only bound as #26's `_new_changelog_stanza_lines` — refactored into one shared helper both now call) reads the proposed version and the full text of the new top stanza from the diff.
  2. Compare against what's currently published for this package in the *current Ubuntu devel series*, checking `<devel>-proposed` first and falling back to `<devel>` (Release pocket) — per seb128's framing ("what is in $devel-proposed / $devel (use proposed if there is a version there otherwise $devel)"). Not per-target-branch: even a merge MP (which targets `debian/*`, not an Ubuntu series) is compared against devel, since that's where a sponsored upload actually lands. SRU MPs targeting an older series aren't handled correctly by this yet — consistent with SRU being deferred everywhere else in this bot (see #20's `mp-target-branch-rules` note).
  3. `archive_lookup.version_compare` (new; `is_at_least` now built on top of it) does the three-way comparison:
     - proposed newer → nothing to do.
     - proposed older → bounce: "The proposed version is older than the one in the archive and needs to be rebased" + `vote="Needs Fixing"`.
     - proposed equal → fetch the archive publication (`archive_lookup.published_source`, new — `getPublishedSources(..., version=..., status="Published")`) and its changelog text (`archive_lookup.changelog_text`, new — resolves `SourcePackagePublishingHistory.changelogUrl()` then fetches it over plain HTTP), extract its first stanza (`_first_changelog_stanza_text`), and compare content against the proposed entry (`_normalize_changelog_entry` — whitespace-tolerant): matching content → "this change was already uploaded, the MP can be closed" (comment only, no vote, informational like #25's empty-diff case); different content → "an upload with the same version and different content already exists, needs a rebase" + `vote="Needs Fixing"`.
* **Return value deviates from every other check in this module:** since a fired result maps to two different conclusive states (`WAITING_ON_CONTRIBUTOR` for the two "needs fixing" cases, `DONE` for "already uploaded, matching content"), `check_stale_version` returns `"needs_fixing"` / `"done"` / `False` instead of a plain bool, and `main.py`'s Check 6 branches on the string rather than treating any truthy return as one fixed outcome. This is a deliberate, documented exception to the bool-returning convention, not an oversight — kept to a single check rather than splitting into two (which would double the archive/network lookups on every "same version" MP for no benefit). Two more outcomes were added the same day: `"pending"` (see the grace-period bullet below) and `None` (see #28) — both bullets below.
* **Grace period for case 3a (seb128, same day):** git-ubuntu's own importer notices when a merge has landed in the archive and auto-closes the MP itself, but this can take a while. Commenting "this can be closed" immediately risks doing so right as (or just before) Launchpad closes it on its own — noisy and potentially confusing. Fix: in the matching-content (3a) branch, check the publication's `date_published`; if younger than `_RECENT_UPLOAD_GRACE` (24h), return `"pending"` instead of commenting. `main.py` handles `"pending"` by recording a `PENDING_ARCHIVE_IMPORT` status **without** passing `facts=new_facts` to `update_status` — deliberately, since `StateManager.update_status` only touches the stored `facts` column when a caller passes one; omitting it leaves the previous snapshot (or lack of one) untouched, so the top-level facts-unchanged gate can't skip this URL, and every subsequent run retries until either the grace period elapses or `check_administrative_state` (Check 1) catches the MP once Launchpad auto-closes it. Fails safe to *not* deferring (comment as normal) if `date_published` is missing or a comparison raises — never gets stuck refusing to comment forever over an unreadable date. Only applies to 3a: 3b (different content at the same version) always needs a rebase regardless of upload recency, since there's nothing for git-ubuntu's importer to reconcile there. **Live-validated** against real MP #506927 (svxlink) twice on 2026-07-03: first run found the archive publication (53 min old at the time) and correctly returned `"pending"` with no comment; a prior run (before the grace period was implemented) had briefly shown what the premature "already uploaded" comment would have looked like.
* **`changelog_text` fetch: deliberately plain, not routed through the authenticated session.** Considered signing the request via the bot's launchpadlib session instead of raw `urllib.request.urlopen` — traced how launchpadlib itself fetches file content (`HostedFileBuffer` in `lazr.restfulclient/resource.py` calls `hosted_file._root._browser.get(url)`, an authenticated GET against an arbitrary URL, which is what `preview_diff.diff_text.open().read()` uses under the hood elsewhere in this bot). seb128 confirmed the standard tooling pattern for `changelogUrl()` specifically is a plain unauthenticated `urlopen` — it points at a publicly readable librarian file, not a permission-gated one — so the original plain-`urllib` implementation was correct as written; no change made.
* **Live-validated, 2026-07-03**, against real MP #506927 (svxlink): `--dry-run --verbose --force` end to end. Correctly walked through all 6 checks (svxlink's `(LP: #2154883)` reference matched the bug's own task, `2154883` — fix MP, not a merge, so check 2 correctly skipped it) and `check_stale_version` correctly resolved case 3a: proposed `25.05.1-4ubuntu1` == the published `stonking-proposed` version, `changelogUrl()` → `urlopen()` fetched the archive changelog with no auth issue, content matched, and it produced "this change was already uploaded, the MP can be closed" (comment only, no vote — dry-run, nothing actually posted). Confirms the fetch mechanism works against real Launchpad, not just fakes; the "not yet live-validated" caveat below no longer applies.
* **Backlog, not built:** the same comparison for a bug's attached patch (extract the proposed version from the patch's `debian/changelog` hunk instead of an MP diff — see STATUS.md item 10). Also backlog: actually setting the MP's `queue_status` to `Merged` in the 3a ("already uploaded") case instead of just commenting, once it's confirmed whether git-ubuntu MPs' status-write rejection (#25) applies to every status or just the ones this bot had been trying to write — needs live investigation into what the bot's account can actually do, flagged as a `TODO` in `checks.check_stale_version` itself.
* **Tests:** `tests/test_archive_lookup.py` gained `version_compare`, `published_source` (found/not-found/lookup-failure), and `changelog_text` (fetches resolved URL / URL unresolvable / fetch failure) coverage, all against fakes — no real network or Launchpad call. `tests/test_mp_checks.py` gained newer/older/`-proposed`-takes-precedence/matching-content/different-content cases plus lookup-failure/structural-false coverage for every step (devel series unknown, nothing published, lookup failure, publication record missing, changelog unfetchable, diff unreadable) and a non-MP resource type, plus the grace-period deferral cases (recent upload defers; old upload doesn't; the grace period only applies to 3a, not 3b; missing/unparseable `date_published` fails safe to not deferring).

## 28. Lookup Failures Must Not Be Cached as "Nothing to Flag" (DONE)
**Date:** 2026-07-03
* **Problem, found live:** re-running the bot against real MP #506927 (svxlink) hit a genuine network timeout fetching the archive changelog (`archive_lookup.changelog_text`, added in #27) — a transient infrastructure failure, not a real "nothing wrong" result. Before this fix, every check that wraps an external lookup in a fail-safe `try/except` (by design, per this bot's whole philosophy — see #20, #25, #26, #27) returned a plain `False` on *any* failure, indistinguishable from "checked thoroughly, genuinely nothing to flag." Since the pipeline fell through to the LLM phase's `READY_FOR_HUMAN` branch, which unconditionally called `state_manager.update_status(url, ..., facts=new_facts)`, a transient failure got permanently cached: the top-level facts-unchanged gate in `triage_url` would skip re-triaging that URL on every subsequent run until the contributor changed something — meaning a check that failed due to a network blip would never get a second chance to actually run. Flagged by seb128 directly in response to seeing this happen live, generalized proactively ("better earlier than later, we will eventually need to deal with that") beyond just `check_stale_version` to every check with this shape.
* **Decision:** every check that can fail an external lookup now returns three values instead of two, using `None` (not `False`) for "couldn't determine":
  - `False` = definitively checked, nothing to flag. Stable, safe to cache.
  - truthy (`True` / `"needs_fixing"` / `"done"` / `"pending"`) = fired, as before.
  - `None` = an external lookup/fetch raised — genuinely undetermined, not a confirmed clean pass. Retriable, must not be cached.
* **Where this applies, concretely:**
  - `_is_merge_proposal`: the `lp_obj.bugs` fallback call failing now returns `None`, not `False` ("not a merge"). `check_target_branch` propagates it.
  - `check_changelog_bug_reference`: `_lp_bug_numbers_from_new_changelog_entry` returning `None` (diff genuinely unreadable, a fetch failure) is now distinct from returning an empty set (diff read fine, nothing cited — a stable fact, whether because there's no changelog section at all or the entry just doesn't mention a bug). Per-bug lookup failures are tracked separately from confirmed mismatches: a *confirmed* mismatch still fires even if some *other* cited bug's lookup failed (we already have a definite problem to report); zero confirmed mismatches plus at least one lookup failure returns `None` rather than the previous "skip silently."
  - `check_stale_version`: every archive/diff lookup failure (diff unreadable, devel series lookup failed, `ubuntu_versions`/`published_source`/`changelog_text` failed) now returns `None`. Structural non-applicability (URL doesn't parse to a package, diff read fine but has no changelog section or an unparseable header, genuinely nothing published yet for this package/series) still returns `False`.
  - The shared diff-reading helpers (`_changelog_diff_lines`, `_new_changelog_stanza_lines`, `_proposed_changelog_entry`) had to adopt the same None(=unreadable)/False(=readable-but-empty) split internally so callers three levels up could tell the difference without re-deriving it. `_changelog_diff_lines`'s "no debian/changelog section" fallthrough changed from `None` to `False` for this reason — a small breaking change to a private helper's contract, not to any public check's behavior.
* **`main.py`:** `triage_url` now tracks an `inconclusive` flag, set whenever any of the 6 checks returns `None` (checked via `is None`, so `None` and `False` are never conflated even though both are falsy for the existing `if fired:` dispatch — no changes needed to that half of the logic). All three LLM-phase terminal branches (`SYNCED`, `INCOMPLETE`, `READY_FOR_HUMAN`) now pass `facts=None if inconclusive else new_facts` instead of unconditionally `facts=new_facts`. `SYNCED`/`INCOMPLETE` are bug-only outcomes and none of the bug-facing checks (only `check_administrative_state` applies to bugs, and it has no external-lookup surface) can currently produce `None`, so this is future-proofing for those two branches rather than fixing an active bug there — but `READY_FOR_HUMAN` is reachable by MPs today and this is exactly the path that was silently swallowing the svxlink-style timeout.
* **Follow-up, same day, now DONE:** `check_mp_conflicts` and `check_empty_diff` read `preview_diff` attributes with no `try/except` at all — a lazily-fetched attribute access (first touch of `.preview_diff` on a real launchpadlib object) could itself raise on a network failure, and that would propagate all the way out of `triage_url` uncaught, likely killing an entire `--all` run mid-queue. This is a different problem from the rest of #28 (crash-safety, not cache-correctness), initially left as a backlog item, then fixed right after: both functions now wrap the `preview_diff` fetch and its `conflicts`/`diff_lines_count` attribute reads in a `try/except`, returning `None` on any exception (same convention as everywhere else in this module) instead of letting it propagate. `main.py`'s Check 3/4 dispatch already handled `None` uniformly (it was added defensively for all 6 checks when #28 was built, even though checks 1/3/4 couldn't produce `None` at the time), so no `main.py` change was needed here. `check_empty_diff` previously had no dedicated unit tests at all; picked up basic True/False coverage alongside the new None-on-failure test while touching it.
* **Tests:** `tests/test_mp_checks.py` — `_is_merge_proposal`/`check_target_branch` return `None` when the bugs fallback raises (renamed from a "fails safe to False" test to reflect the new expectation); `check_changelog_bug_reference` returns `None` on diff-unreadable and on every-cited-bug-lookup-failing, but still fires on a confirmed mismatch even with a co-occurring lookup failure; `check_stale_version` returns `None` (not `False`) for every lookup-failure branch, with new structural-`False` tests added specifically to prove the distinction survives (nothing published yet — a `{}` result, not a lookup failure; diff readable but touches only `debian/control`). `tests/test_state_facts.py` gained an end-to-end test, `test_inconclusive_check_does_not_persist_facts_so_next_run_retries`, that runs `main.triage_url` twice against the same inconclusive MP and asserts (via captured stdout) that the second run actually re-executes the full pipeline rather than being silently skipped — proving the fix at the integration level, not just unit-testing the three-value return contract in isolation.

## 29. Warn Upfront When `opencode` Isn't Installed (DONE)
**Date:** 2026-07-03
* **Problem, found live:** seb128 moved the bot into a container to keep the host system clean and hadn't installed `opencode` there yet — and was surprised nothing complained loudly. `llm_reviewer._query_llm` already caught `FileNotFoundError` and printed `WARNING: 'opencode' command not found...` (#9's fail-safe-to-human design meant this was never a crash), but that warning only appears once triage reaches the LLM phase for an SRU/sync-shaped bug, buried per-item in a long `--all` run's output — easy to miss entirely if the queue's first several items don't happen to need the LLM phase, and even when visible it reads like a per-item hiccup, not "the LLM phase is disabled for this entire run."

The existing per-call warning in `llm_reviewer._query_llm` is unchanged — still useful in `--verbose`/debugging — this is additive, not a replacement.
* **Rationale:** the fail-safe behavior itself (never crash, never silently pass — fall through to human review) was already correct per #9; the gap was purely *visibility*. A user should know immediately, not partway through a long queue scan, that an entire review phase is offline.
* **Net effect:** deterministic checks (1–6) are entirely unaffected — they have no `opencode` dependency and keep working exactly as before, so the bot is still useful (and correctly conservative) with `opencode` missing. This warning exists so that fact is obvious, not just true.

## 30. A Permanently-Missing `preview_diff` Must Not Loop Forever (DONE)
**Date:** 2026-07-03
* **Problem, found live:** the first real `--interactive` prep run flagged MP #503471 (plymouth) as `inconclusive` (see #28). Investigating with `--verbose` showed `lp_obj.preview_diff` was cleanly `None` — not an exception, Launchpad genuinely has no diff for this MP — and the MP was created **~3 months** earlier (`date_created` 2026-04-10, checked live 2026-07-03). seb128 confirmed diff generation normally isn't slow (the human-facing yellow "Launchpad is generating the diff" box on the MP page clears within minutes), so this is a stuck/failed Launchpad job that was never retried, not a transient state.
* **Two separate bugs this uncovered:**
  1. `check_mp_conflicts`/`check_empty_diff` treated a cleanly-`None` `preview_diff` as "no conflicts"/"not empty" (`False`, silently cached as clean) — wrong, since there's no data to have checked at all.
  2. `_changelog_diff_lines` (used by checks 5/6) correctly returned `None` for the same condition, but with *no* age awareness, that's `None` **forever** for an MP like this — `inconclusive` stays `True` on every run indefinitely, re-invoking the LLM phase pointlessly on every `--all` pass (now a real `opencode` call, not just a skipped one, since #29).
* **Decision:** new `checks._diff_missing_is_still_generating(lp_obj)`, checked wherever `preview_diff` is cleanly `None` (`check_mp_conflicts`, `check_empty_diff`, `_changelog_diff_lines`): compares `lp_obj.date_created` against `_MISSING_DIFF_GRACE = timedelta(hours=1)`. Within the grace period → `None` (retriable, matches the existing "still generating" assumption). Past it → `False`, same bucket as "diff exists but has no debian/changelog section" / "no conflicts" / "not empty" — a stable, cacheable fact, not a lookup failure. Missing/unparseable `date_created` fails safe to "still generating" (`True`/`None`), the more conservative assumption, mirroring `check_stale_version`'s `date_published` grace-period handling (#27).
* **Why caching a permanently-missing diff as `False` is safe:** `facts.build_facts` already fingerprints `diff_id` (`preview_diff.self_link`), `diff_lines_count`, and `has_conflicts`, all `None`/`False` when `preview_diff` is `None`. If Launchpad ever does generate a real diff later, those fields change, the top-level facts-unchanged gate in `triage_url` detects it, and the MP gets properly re-triaged with real diff data — the same mechanism that already makes the whole facts-based re-triage design (#10) safe.
* **Live-validated, 2026-07-03:** before the fix, MP #503471 triaged as `inconclusive` on every run. After: `check_mp_conflicts`, `check_empty_diff`, `check_changelog_bug_reference`, and `check_stale_version` all resolve to `False` consistently, reaches `READY_FOR_HUMAN`, and (unlike before) persists cacheable facts — confirmed via a real `--dry-run --verbose --force` run against the live MP.
* **A real regression caught before shipping, not by the unit suite:** to stop the WARNING printing once per affected check (up to 4× per stuck MP per run), `_diff_missing_is_still_generating` was briefly wrapped in `functools.lru_cache`, keyed on `lp_obj` identity. This crashed immediately against the *real* MP (`TypeError: unhashable type: 'Entry'` — launchpadlib's `Entry` objects aren't hashable) but every one of the 150 unit tests still passed, because `tests/fakes.py`'s `FakeMP` is a plain object with default (hashable) identity — another concrete case of this project's running theme (#16, #20 §validation, #26, #27, #28) that fakes can silently diverge from real API object behavior, and only a live run catches it. Reverted rather than fixed with an `id(lp_obj)`-keyed dict, since `id()` reuse after garbage collection across a long `--all` run could cause an incorrect cache hit for an unrelated object — not worth the risk for a purely cosmetic dedup. Left as a documented, low-priority backlog note in the function's own docstring; the repeated print is harmless.
* **Backlog, explicitly not built (seb128's idea, worth doing later):** a "notify service maintainer" path — post to a Matrix (public) or Mattermost (private) channel when the bot hits a Launchpad-side problem a *contributor* can't fix (a stuck diff generation like this one; also a natural fit for #25's git-ubuntu `queue_status`-write rejection, so infra-capable people learn about permission/API problems without it ever reaching or confusing the contributor). Deliberately not built now — needs a new notification backend/API token, out of scope for this session. `_diff_missing_is_still_generating`'s existing `print(...)` is the natural spot to eventually route into it.
* **Tests:** `tests/fakes.py`'s `FakeMP` gained `date_created` and `no_diff` constructor params (the latter forces a genuinely-`None` `preview_diff`, distinct from the default-`FakeDiff` behavior of leaving `diff` unset). `tests/test_mp_checks.py` gained: missing-diff-but-fresh-MP → `None` and missing-diff-past-grace → `False` for both `check_mp_conflicts` and `check_empty_diff`; missing `date_created` fails safe to "still generating"; the same past-grace → `False` propagation through `check_changelog_bug_reference` and `check_stale_version` (via `_changelog_diff_lines`).

## 31. Aggregated Findings Model: `closing` / `incomplete` / `question` (DONE -- implemented 2026-07-06, see #44)
**Date:** 2026-07-03
* **Problem:** `triage_url`'s dispatcher is strict first-fire-wins — the moment any check fires, it posts its own comment/vote and returns, so later checks in the list never run *this* pass. An MP with two simultaneous problems (say, a bad changelog bug reference **and** a stale version) only ever hears about the first one; the contributor fixes it, waits for the next bot run (or worse, the next human sponsor pass, which can be a week+ away per seb128), and only then learns about the second. Also, deterministic-check bounces and the LLM phase's own verdict currently post as separate comments, which reads as two unrelated bots talking instead of one coherent review.
* **Decision (seb128):** every check outcome now has one of three severity tiers — named `closing`/`incomplete`/`question` specifically to avoid colliding with the pre-existing, unrelated `inconclusive` (a check returned `None`, a lookup failed — see #28, [[check-lookup-failure-vs-nothing-to-flag]]). A naming collision here was caught and avoided during design, not after.
  - **`closing`** — the item is already resolved; no review is needed. Still short-circuits exactly as today: further checks don't run, and the comment is a terse, situation-specific message (not the shared template below). Current members: `check_administrative_state`, `check_empty_diff`, `check_stale_version`'s `done` outcome, and (once folded in) the LLM phase's `SYNCED` outcome.
  - **`incomplete`** — a hard requirement; the contributor must act before this can be sponsored. Unlike today, checks in this tier no longer stop the pipeline on first fire — every remaining check still runs, so all simultaneous `incomplete` findings surface in the same pass. Current members: `check_target_branch`, `check_mp_conflicts`, `check_changelog_bug_reference`, `check_stale_version`'s `needs_fixing` outcome, and (once folded in) the LLM phase's `INCOMPLETE` outcome.
  - **`question`** — non-blocking, advisory. Never changes status/vote and never stops the pipeline; the run proceeds exactly as if it hadn't fired. No existing check produces this tier yet — it's reserved for future soft findings (an SRU-rule nitpick, an LLM-noticed style issue that isn't a blocker) so they don't have to be forced into `incomplete` just because that was previously the only bounce tier available.
  - **Priority for the one status/vote a run ends with:** `closing` > `incomplete` > `question` — only the highest tier present drives the outcome, but lower tiers still contribute their message text to the comment.
* **One templated comment, not one per check.** Intro line, posted once regardless of which sections follow: *"Thanks for your contribution! The automated review spotted the following points:"* Then up to two sections, each omitted entirely if it has no findings:
  - **"Needs fixing before this can be sponsored:"** — bullet list of every fired `incomplete` finding's message.
  - **"Nice to have (non-blocking):"** — bullet list of every fired `question` finding's message, e.g. *"None of these block the upload, but you may want to address them now — before a sponsor reviews this, or in a future contribution."*
  A run with zero findings in either tier posts no comment at all, same as today's silent `READY_FOR_HUMAN` (no "all clear!" noise on every clean item). `closing` outcomes never reach this template — they keep their own terse message.
* **LLM phase folds into the same pool, not a separate write path.** `llm_reviewer.triage_bug`/`triage_mp` stop returning a ready-to-post `(status, comment)` pair to write directly; instead they contribute findings (tier + message) into the same collection the deterministic checks feed, and the render step described above is the *only* place a comment actually gets built. `SYNCED` stays `closing`-tier and bypasses the template, same as the deterministic closing checks — it's "already resolved," not "here's feedback." The LLM is explicitly allowed to emit `question`-tier findings, not only `incomplete` — a technically-acceptable-but-improvable SRU justification shouldn't have to be forced into a hard blocker just because that used to be the only option.
* **Vote mapping (per #25, unchanged in kind):** `closing` → no vote, or the existing situation-specific handling (`check_empty_diff` already has no vote, nothing in the enum fits "looks merged"). `incomplete` → `vote="Needs Fixing"` on the one aggregated comment, regardless of how many `incomplete` findings contributed to it. `question`-only → no vote; a question never blocks, so there's nothing for a review vote to signal.
* **Interactive mode UX:** explicitly deferred — seb128: "let's talk as needed before moving to next steps." Working assumption during design was a single `[y/N]` approving the whole aggregated comment (not one prompt per finding, since the reviewer is approving one coherent verdict, not auditing sub-rules independently), but this isn't locked in; revisit when actually building the write path.
* **Addendum: `inconclusive` must gate posting the aggregated comment, not just facts persistence (seb128).** Spotted while live-validating #33's timeout work: today's per-check bounce comments are self-contained ("your version is stale, please rebase") and never claim to be a complete review, so an inconclusive sibling check just means reduced coverage for that pass, not wrong content. That stops being true once #31 ships — the whole point of the aggregated comment is that a contributor can treat it as *the* complete list of what to fix this round. If one contributing check timed out while others fired normally, posting the aggregate as-is implicitly claims a completeness it doesn't have: the contributor fixes what's listed, then next run turns up something the bot could have caught this time but didn't, because of an unlucky lookup failure — worse than staying silent, since it *looks* authoritative. Rule: a pass with any `None` (inconclusive) result must not post the `incomplete`/`question` aggregate at all — same "don't cache, retry next run" treatment `inconclusive` already gets for facts persistence (#28), now extended to gate the write itself, not just what gets cached about it. `closing` is unaffected — it short-circuits on its own terse, situation-specific message before other checks even run, so it's never a partial aggregate in the first place.
* **Status: DESIGNED only, not implemented.** This is a genuine refactor of every check's return contract (bool/three-value → tier + message findings) and the `main.py` dispatcher, plus the `llm_reviewer` integration — foundational enough (same shape as #10, #20) to record the design before writing code, per this project's usual practice.

## 33. Launchpad Session Timeout + Fail-Safe Per-Item/Login Error Handling (DONE)
**Date:** 2026-07-03
* **Problem, found live:** the #32 timing work's first real `--all --dry-run --verbose` run against the live queue sat for **1h33m wall-clock** with the log silent for the last 27+ minutes, stuck mid-`check_stale_version` on item 45/90. `ss` showed one idle `ESTABLISHED` TCP connection to Launchpad's API — the process was genuinely parked waiting on a response that would never come, not merely slow. Root cause: `launchpad_client.LPClient` calls `Launchpad.login_with(...)` with no `timeout=`, so every launchpadlib call (this session is reused for the whole run) waits forever by default. `archive_lookup.py`'s two raw `urllib` calls already pass `timeout=15`, but the far more frequently used launchpadlib path had no equivalent.
* **Fix 1 — bound the session:** new `_LP_TIMEOUT_SECONDS = 30`, passed as `Launchpad.login_with(..., timeout=_LP_TIMEOUT_SECONDS)`. Traced (not guessed) what this actually does: it becomes a raw `socket.settimeout(30)` on the underlying `httplib2` connection (`RestfulHttp` subclasses `httplib2.Http`, which passes `timeout` straight to the socket). On expiry this raises a bare `TimeoutError`/`socket.timeout` — not one of `lazr.restfulclient.errors`' HTTP-error classes, since those model real HTTP responses, not connection failures. Confirmed no retry logic exists anywhere in `httplib2`/`lazr.restfulclient`/`launchpadlib` for this exception (read `Browser._request_and_retry`, `Http._conn_request`, `Http.request`'s exception handler directly — all either re-raise immediately or only retry on `502`/`503` HTTP *responses*, never on a socket timeout).
* **Important caveat, also confirmed live, not assumed:** `socket.settimeout(N)` bounds *each individual blocking call* (connect/send/each `recv`), not the request as a whole. A slow-trickling response or a redirect hop (Launchpad commonly serves hosted files like a diff via a redirect to `launchpadlibrarian.net` — a second sequential request with its own fresh allowance) can each individually stay under 30s while the operation as a whole takes several multiples of it. Live-validated in the #33 clean `--all` run itself: `check_changelog_bug_reference` on one item took 102.52s, `check_stale_version` on another took 165.29s — both well past "30s" but each explainable as ~3 individual near-the-limit reads/hops rather than one call exceeding the bound. `_LP_TIMEOUT_SECONDS` is therefore a soft per-syscall guard against the *original* problem (an indefinitely stuck connection), not a hard per-check wall-clock ceiling. A true hard deadline would need out-of-band cancellation (e.g. a worker thread abandoned at a deadline, since Python has no clean way to force-kill a blocked syscall) — considered and deliberately not built; the existing fail-safe (`None`/retriable, see #28) already produces a correct outcome once a call does eventually fail, just not always a fast one.
* **Fix 2 — per-item catch-all in `main.triage_url`:** several launchpadlib attribute reads have no `try/except` of their own (`facts.build_facts`'s `resource_type_link`/`preview_diff`/`description`/`tags`/`bug_tasks`; `checks.check_administrative_state`'s `queue_status` and `_relevant_ubuntu_tasks`'s `bug_tasks`/`task.status`; `checks.check_target_branch`'s `target_git_path`) — unlike the lookups in `archive_lookup.py`, which already fail safe internally (§27/§28). Once a timeout bound existed, a stall in any of these would raise straight out of `_triage_url`, propagate through `process_queue`'s loop, and abort the entire `--all` run at that item — silently skipping every later queue item for the rest of that run. `triage_url` (already split into a thin wrapper + `_triage_url` for #32's timing) now also wraps the call in `except Exception: logger.exception(...); return None` — full traceback logged (nothing hidden for debugging), but the run continues to the next item. Nothing gets persisted for a caught failure, so the URL is retried from scratch next run, consistent with every other retriable-failure path in this codebase.
* **Fix 3, found live during testing, not anticipated in the original design:** the per-item catch-all does **not** cover `LPClient(...)` construction in `main()` — that runs once at startup, before any `triage_url` call. Confirmed live by temporarily hacking `_LP_TIMEOUT_SECONDS` to 1 and clearing the local launchpadlib WADL cache (`SPONSORING_BOT_LP_CACHE`) to force a genuine network round-trip instead of a cached hit: the process died with a 60-line raw `TimeoutError` traceback and exit code 1, entirely outside any of this bot's own logging. Fixed by wrapping the `LPClient(...)` call in `main()` in its own try/except: `logger.error("Failed to authenticate to Launchpad: %s", e)` then `sys.exit(1)` — same non-zero exit for cron/monitoring to notice, but one clean line instead of a raw traceback. Re-verified live with the same forced-timeout setup: clean single-line error, `EXIT_CODE=1`. There is no per-item fallback possible here (no session, nothing this run can do), so exiting is correct — unlike the per-item case, there is no "next item" to move on to.
* **Live-validated end to end, a full `--all --dry-run --verbose` run against the real queue (90 items) after all three fixes:** exit code 0, all 90 items completed, zero unexpected errors, zero hangs. Total ~23.1 min wall-clock (sum of sequential per-item times), median item 8.84s, mean 15.41s (skewed by a handful of slow items — `check_stale_version` and `check_changelog_bug_reference` alone account for ~60% of total run time across all 90 items, consistent with #32's single-item finding that these two live-lookup checks dominate cost). Slowest single item: 269.62s (`rust-sequoia-sqv` #502068) — traced to `check_changelog_bug_reference` and `check_stale_version` **each independently re-fetching the same MP diff content from scratch** (no memoization between checks within one `triage_url` call — see the backlog note below) and each separately hitting the slow-trickle/redirect soft-timeout behavior described above. No item in this run got stuck the way item 45 did in the pre-fix run; every item that hit a real Launchpad problem failed safe (`None`, logged, retried next run) and the run kept moving.
* **Outcome breakdown from the same clean run (not just timing — what the triage actually found), worth recording since this is the first full-queue pass with all fail-safes in place:** 90 items = 50 MPs + 40 bugs (7 of the 40 had no Ubuntu task the admin check could match, falling straight through to human review). Deterministic checks 1–6 fired: `check_stale_version` 28× (23 `needs_fixing`/stale, 4 `done`/already-uploaded, 1 duplicate-version), `check_mp_conflicts` 4× (clustered in ROCm/HIP packages — `firmware-sof`, `hipcub`, `hiprand`, `hipblas` — real conflicts, not the old `has_conflicts`-vs-`preview_diff.conflicts` false-positive bug from #16), `check_administrative_state` 2× (bug already resolved). **Zero** `check_target_branch` wrong-target bounces and **zero** `check_changelog_bug_reference` mismatches this run — the first is a good sign #20's merge/fix/SRU classification isn't over-bouncing plain fixes anymore (the bug #20 exists to fix), the second is either genuinely clean data or just this run's luck, one pass isn't enough to call a trend. 56 items reached the LLM phase (all 6 checks clean): 53 `READY_FOR_HUMAN`, 3 `INCOMPLETE` (bugs 2139024, 2148318, 2144629 — inadequate SRU template). Of the 38 bugs `triage_bug` classified: 20 SRU, 1 sync request, 17 neither. 2 items were `inconclusive` — one of them, `google-osconfig-agent` MP #504883, is a live real-world instance of exactly the scenario #31's addendum exists for: an earlier check failed to determine its result on that item, *and* `check_stale_version` still fired and posted its own bounce independently afterward. Harmless today (bounce comments are self-contained, per the addendum's reasoning) but concretely confirms the addendum isn't a hypothetical.
* **A red herring during this investigation, worth recording so it isn't re-chased later:** an earlier `--all` run (before this one) showed 77/90 items failing with `sqlite3.OperationalError: no such table: requests`. Initially looked like it might be related to the parallel single-URL timeout experiments run alongside it. Root-caused precisely: those experiments were harmless (`StateManager.__init__`'s `CREATE TABLE IF NOT EXISTS` is idempotent even under concurrent access) — the actual cause was running `rm -f state.db` as a "cleanup" step while that `--all` run was still active in the background. `StateManager` opens a fresh `sqlite3.connect(path)` per call rather than holding one connection open, so the next call after deletion silently created a brand-new, schema-less file at that path. Confirms Fix 2 works well even for a completely unrelated failure mode (data loss under an active run, not a network timeout): the affected items still ran their full check + LLM pipeline correctly and only failed at the final persist step, caught cleanly by the same catch-all.
* **Backlog, not built (seb128, considered and explicitly deferred):**
  - In-process retry (e.g. 3 attempts with backoff) for a check that hits `None`. Deliberately rejected: today's failures are slow *degrading* struggles (100s+), not fast clean timeouts, so an immediate retry risks hammering an already-struggling endpoint and multiplying one slow item into several times slower — worse on exactly the days it matters. The existing "retry via next cron run" is free, already correct, and gives Launchpad real recovery time a same-process retry wouldn't.
  - Per-item diff-content memoization (the redundant-fetch cause of the 269.62s outlier above): `_changelog_diff_lines` is called independently from `check_target_branch` (via `_debian_target_suite`, bounce-message path only), `check_changelog_bug_reference`, and `check_stale_version`, with no caching. Under today's dispatcher, only checks 5 and 6 ever co-occur in one pass (check 2 short-circuits on fire), so the real overlap is just those two. Fix considered: a lazy, per-item cache closure created fresh in `_triage_url` (not `functools.lru_cache` keyed on `lp_obj` — already tried and reverted in #30, real launchpadlib `Entry` objects aren't hashable; a closure avoids hashing/keying `lp_obj` at all). Open question resolved during design-only discussion: a cached failure (`None`) should be reused too, not just cached successes — otherwise the second caller re-attempts independently and reintroduces the exact compounding this would fix. Not implemented; a real signature change across several `checks.py` functions plus `_triage_url`, deferred as "interesting but not needed right now."
* **See also:** the #31 addendum above (`inconclusive` must gate the aggregated comment) was prompted directly by this investigation.

## 35. Suppress Bounces Once a Human Is Already Engaged (DESIGNED, not built)
**Date:** 2026-07-04
* **Problem (seb128, found by manually checking items from a fresh full-queue dry run):** the bot's whole purpose is *early* feedback, before a human sponsor spends time on an item. Today it has no concept of "a human already commented here" at all — it'll happily post its own bounce on an item a sponsor is actively reviewing, which is redundant at best and confusing (two different "reviewers" talking) at worst.
* **Core rule, agreed:** skip posting a finding if a comment from anyone other than the submitter (and not the bot itself) exists on the item. Explicitly **not** restricted to `~ubuntu-dev`/uploader comments — seb128: new/non-core contributors sometimes leave real review feedback too, and that should count just as much as a core-dev comment. (Checked `~/hacking/sponsoring/ubuntu-sponsoring/ubuntu_sponsoring/sponsors_page.py`'s `htmlify_name` for precedent — that script only ever *displays* the last commenter, bold/italic by `~ubuntu-dev` membership + `person_can_upload`; it doesn't filter anything, so there's no existing logic to reuse here, only the comment-fetch pattern.)
* **Must exclude the bot's own account.** Non-negotiable — without this the bot would see its own first bounce comment and permanently skip itself on every later run. `launchpad_client._already_posted` (line 135) already fetches `lp_obj.messages` (bugs) / `lp_obj.all_comments` (MPs) keyed against `self.lp.me.self_link` for the existing comment-dedup logic; this reuses the same fetch and identity check.
* **Other bot/service accounts (git-ubuntu's importer, janitor, etc.) are explicitly deferred, not solved now.** A comment from one of those would count as "human engaged" today (a false negative — the bot goes silent even though no human actually looked), which isn't quite right, but seb128 agreed this is fine to accept for v1 rather than build an exclusion list preemptively. Revisit if it causes real problems in practice.
* **Scope: only suppresses `incomplete`/`question`-tier output, never `closing`-tier.** This is the one correction that came out of discussion, and it matters: seb128 pointed out the common real path to closing an MP is a sponsor commenting "looks good, uploading" *before* the actual upload/close happens. If the human-engaged rule blocked everything unconditionally, an MP could sit forever skipped even after the archive genuinely gets the matching upload, should git-ubuntu's auto-close not fire for some reason (see backlog note below). So the rule only ever suppresses a check's `incomplete`/`question` output; a `closing` outcome always still fires, comments, and acts, regardless of who said what. This maps directly onto #31's tier taxonomy rather than being a separate mechanism:
  - **`closing`, never suppressed:** `check_administrative_state`, `check_empty_diff`, `check_stale_version`'s `done` outcome (this is literally "does what's in the archive match the MP", `checks.py` line ~778 — the `proposed == archive version, content matches` branch).
  - **`incomplete`, suppressible:** `check_target_branch`, `check_mp_conflicts`, `check_changelog_bug_reference`, `check_stale_version`'s `needs_fixing` outcome (both the stale-rebase and duplicate-version cases).
  - Since today's dispatcher is still #31's not-yet-built tiered model, in practice this means: `check_empty_diff` and `check_stale_version` must always run to completion regardless of human engagement (their closing-vs-incomplete split isn't known until they've done the work), and only their *incomplete*-flavored result gets suppressed; `check_target_branch`/`check_mp_conflicts`/`check_changelog_bug_reference` have no closing case at all, so those can bail out early once human-engagement is known, which is a real efficiency win for `check_changelog_bug_reference` specifically (the expensive diff-content fetch).
* **Efficiency/ordering (worked through with seb128 by reading `facts.py`/`checks.py` directly, not guessed):** `check_administrative_state` and `check_mp_conflicts`/`check_empty_diff` cost nothing extra beyond what `build_facts` already fetched (`queue_status`, `bug_tasks`, `preview_diff.conflicts`/`diff_lines_count`); `check_changelog_bug_reference` (diff content + per-bug lookups) and `check_stale_version` (archive + madison lookups, plus a redundant second diff fetch per #33's backlog) are the genuinely expensive ones. The new human-engaged check itself costs one new call (`lp_obj.messages`/`all_comments`, not fetched anywhere else today). Best ordering: `build_facts` → facts-unchanged gate → `check_administrative_state` (cheap, closing, and correctly takes priority — no reason to even ask about comments if the task's administratively done) → the new human-engaged check → remaining checks. This avoids paying for the comments-fetch on the ~2% of items `check_administrative_state` already resolves for free.
* **Since-current-diff scoping, MP side decided, bug side still open.** A comment should only count if made *after* the item's current revision, not ever in the whole thread — otherwise one stale human comment on an old push would silently suppress the bot forever on a completely new, unreviewed push. For MPs: `preview_diff.date_created` (already read for #30's grace-period logic) is a clean anchor — a fresh push generates a new diff with a new timestamp. For bugs there's no equivalent: no diff, and the natural candidate (an attached patch's `date_created`) is blocked by the same lpcli attachment-visibility gap noted in #30 (canonical/lpcli#23/#24). Bugs mostly change via description edits (the SRU/sync template), already fingerprinted by `facts.build_facts`, not repeated pushes — so "since current diff" may not even be the right frame for bugs. **Left open, needs a decision before implementing the bug side** — MPs can proceed without waiting on this.
* **Facts persistence:** a suppressed pass should persist facts, same as a clean outcome — this is a stable, determined state (not a lookup failure), so the existing facts-unchanged gate correctly avoids redundant re-checks next run, and correctly resumes real checking the moment a genuinely new push changes the diff identity.
* **Interaction with the LLM phase:** symmetric treatment — the LLM's `INCOMPLETE` tier is suppressible under the same rule, `SYNCED` (closing) isn't. ~~A suppressed finding still short-circuits the rest of the pipeline exactly as an unsuppressed one would~~ **AMENDED 2026-07-04, see the addendum below — suppressed findings must NOT short-circuit.**
* **Amendment (2026-07-04, seb128 + assistant design review): suppressed findings do not short-circuit.** The original bullet above contradicted the closing-tier exemption: with today's check order, a suppressed `check_mp_conflicts` (check 3) stopping the pipeline means `check_stale_version` (check 6) never runs — so the archive-matches-MP `done`/closing outcome this design specifically protects would be missed, and a human-engaged MP whose upload landed would sit in the queue forever. This converges with #31's keep-evaluating tiered dispatch — **#35 should be implemented on top of #31's machinery, not bolted onto today's first-fire-wins dispatcher.** The efficiency claims earlier in this entry (early bail-out for checks with no closing case) are superseded accordingly.
* **Backlog side-note, swept in (seb128):** when `check_stale_version` finds a version+content match on an `ubuntu/*`-targeted MP (not a Debian merge — doesn't apply there), git-ubuntu's importer should auto-close the MP once it processes the upload. Another instance of the fakes-diverge-from-reality theme (#16, #30).

## 44. Design #31 Implemented: Findings Aggregation (DONE)
**Date:** 2026-07-06

* **Closing tier drops collected findings (seb128, explicit):** check 1, check 4, and check 6's `done` keep their terse own-comment short-circuit; when one fires *after* earlier checks already collected findings, those findings are dropped, not posted. ## 45. Design #35 Implemented: Human-Engaged Suppression (DONE, MP side)
**Date:** 2026-07-06
* **What shipped:** design #35 exactly as specified (including its 2026-07-04 amendment), built on #31/#44's tiered keep-evaluating dispatch as planned. New `checks.check_human_engaged(lp_obj, lp_client)` returns True/False/None: True when any `all_comments` entry is authored by someone other than the MP's `registrant_link` and the bot's own account (`lp.me`), dated after `preview_diff.date_created`.
* **Placement -- lazy, at the very end of the pass:** `main.py` consults it only inside `if findings:`, right before rendering the aggregate. This gets every #35 property for free: closing-tier outcomes (checks 1/4, check 6's `done`/`pending`, LLM `SYNCED`) all `return` earlier, so they are structurally un-suppressible; every check and the LLM have already run (the amendment's "suppression silences output, never skips evaluation"); and the one extra comments fetch is only paid when there is actually something to suppress. The design's old per-check early-bail efficiency ideas stayed superseded.
* **Suppressed outcome:** no comment, no vote, no bug-task change; status `READY_FOR_HUMAN` with a "N finding(s) suppressed: a human reviewer is already engaged" detail, and facts ARE persisted (a determined, stable state) -- the facts-unchanged gate keeps the item quiet until a genuinely new push changes the diff fingerprint, at which point the anchor moves too and old comments stop counting.
* **None path:** unreadable comment history follows #28/#31 -- post nothing, persist nothing, retry next run. (Same failure mode `_already_posted` would hit one call later anyway.)
* **Anchor edge case:** a diff with no `date_created` counts any qualifying comment (err toward staying quiet); in practice a missing diff makes checks 4/6 inconclusive long before this gate.
* **Bug side: not implemented, by design.** `check_human_engaged` returns False for anything that isn't an MP -- the "since current submission" anchor question from #35 is still open. Bugs keep today's behavior unchanged.
